## Project status — read this first

This repo is mid-pivot. It started as a "DOM server" system for a **gaming/entertainment company** (arcade machines, games, tickets, chairs, coupons) and is being repurposed into an **ERP for an international trucking company** (Morocco↔Europe, export/import, dual currency MAD/EUR). The functional spec for the ERP domain lives in an Obsidian vault at `MFAH FLOW/` (repo root) — one `.md` file per module (Trucks, Drivers, Clients, Subcontractors, Missions, Invoices, Dashboard), terse French/English field lists rather than prose.

Current state:
- **Backend gaming-domain removal is done**: all legacy modules (`doms`, `experiences`, `games`, `game-types`, `machines`, `machine-types`, `machine-chairs`, `tickets`/`sync`, `comments`, `coupons`, `cdn`, plus the gaming-only `statistics` module) are gone from `backend/src`, and their Prisma models have been dropped from `backend/prisma/schema.prisma` and the live dev DB via an explicit migration (`remove_legacy_gaming_models`). `prisma/seed.ts` now only seeds `roles` + `Users`.
- **The backend ERP API surface is now complete** per the original plan: `permissions` (see below), `attachments` (shared file-upload plumbing), `trucks`, `drivers`, `clients`, `subcontractors`, `missions`, `client-invoices`, `subcontractor-bills`, `dashboard` — all built, migrated, boot-tested, and exercised live via curl. Frontend work starts next (see below).
- **Dashboard** (`src/dashboard/`) is read-only/aggregation-only — no Prisma model, no writes, single `GET /api/v1/dashboard/summary?startDate=&endDate=&offset=&limit=` endpoint (`DashboardService.getSummary`). Two different scoping rules in the same response, deliberately: mission-period figures (`missionTotal`, `missionsByStatus`, `revenue`/`outstanding` (client side, MAD/EUR), `subcontractorSpend`/`subcontractorOutstanding` (payable side, MAD/EUR), and the paginated `missions` table) are filtered by `Mission.missionDate` when `startDate`/`endDate` are given; `fleetStatus`/`driverStatus`/`overdueClientInvoices`/`overdueSubcontractorBills` are **always a live snapshot of right now**, unaffected by the date range, since fleet state and "what's overdue today" aren't historical figures for a period. `revenue`/`subcontractorSpend` are computed from `ClientInvoice`/`SubcontractorBill` (not raw `Mission.clientPrice`), so a mission with no invoice yet contributes 0 — this is intentional (revenue means *billed*, not *booked*). Went beyond the original Obsidian spec (which only asked for client-side MAD/EUR revenue/outstanding + a table) after the user asked for suggestions — added mission-status pipeline, fleet/driver status, subcontractor spend, and overdue counts.
- **ClientInvoice / SubcontractorBill** (`src/client-invoices/`, `src/subcontractor-bills/`): each is 1:1 with a `Mission` (unique `missionId` FK). `amount`/`currency`/the billed party are always **derived from the mission** at creation (`mission.clientPrice`/`mission.currency`/`mission.clientId` for invoices, `mission.subcontractorCost`/`mission.subcontractorId` for bills — never entered independently), so the number staff see always traces back to one source of truth. `SubcontractorBill` creation is rejected (400) unless the mission is `SUBCONTRACTED`; `ClientInvoice` creation works regardless of `executionMode` (we bill the client either way). Both reject a second create on the same mission (409 — strictly 1:1). `invoiceNumber`/`billNumber` auto-generate the same way as `Mission.reference` (`INV-`/`BILL-<year>-<6-digit-seq>`, collision-retried). `Mission.autoInvoice = true` triggers `ClientInvoicesService.createForMission()` right after mission creation (not the same DB transaction — see `MissionsService.create()` — a failure there is logged, not rolled back, since the mission itself is still valid without it); it **never** auto-creates a `SubcontractorBill`, since that one only exists because staff received a real PDF bill from the subcontractor — inherently a manual action. Both models get their own PDF via the unified `Attachment` table (`CLIENT_INVOICE`/`SUBCONTRACTOR_BILL` owner types were added, not a dedicated file field) — PDFs are always uploaded by staff, never generated by the backend. Payment tracking is `PATCH .../admin/:id/payment` with `{ amountPaid }`; `status` (`UNPAID`/`PARTIALLY_PAID`/`PAID`) and `paidAt` are recomputed server-side, not settable directly.
- **Mission** (`src/missions/`) is the core transaction: `executionMode` is `IN_HOUSE` (requires `truckId`+`driverId`, no subcontractor) xor `SUBCONTRACTED` (requires `subcontractorId`+`subcontractorCost`, no truck/driver) — enforced service-side (`validateAndSanitize`) since Prisma can't express an XOR constraint declaratively; the service also strips whichever side doesn't apply so stored data is never inconsistent. `reference` is auto-generated (`MIS-<year>-<6-digit-seq>`, collision-retried). Money fields (`clientPrice`, `subcontractorCost`) are Prisma `Decimal` — they serialize as **strings** in JSON responses, not numbers. Status transitions go through a dedicated `PATCH missions/admin/:id/status` rather than the general update endpoint, because entering `IN_PROGRESS` on an `IN_HOUSE` mission auto-flips the assigned truck to `EN_MISSION` and driver to `EN_MISSION` (a value added to `DriverStatus` specifically for this), and leaving `IN_PROGRESS` (`FINISHED`/`CANCELLED`) reverts them to `DISPO`/`ACTIF` — done inside one `prisma.$transaction`. `SUBCONTRACTED` missions never touch truck/driver status.
- A **custom per-module permission system** was added on top of the existing single-admin-role check: a `Permission` model (`roleId` + `PermissionModule` enum + `canCreate`/`canRead`/`canUpdate`/`canDelete` booleans, unique per `(roleId, module)`), managed via `PermissionsController` (`/api/v1/permissions/roles/:roleId`, admin-only), enforced by `PermissionGuard` + `@RequirePermission(module, action)` (`src/auth/guards/permission.guard.ts`, `src/auth/decorator/require-permission.decorator.ts`). The `admin` role always bypasses it (same superuser behavior as `AdminRoleGuard`); every other role needs an explicit `Permission` row per module/action or it's denied. New ERP controllers use `@UseGuards(AuthGuard, PermissionGuard)` + `@RequirePermission(...)` per route instead of `AdminRoleGuard`, including for reads (nothing here is public catalog data). `users`/`roles` controllers are untouched and still use `AdminRoleGuard`.
- File attachments: `src/attachments/` has `LocalFileStorageService` (the only code that touches `fs`, path configurable via `UPLOADS_DIR` env var, default `./uploads`) and a single `AttachmentsService` backing one unified `Attachment` table used by **every** entity module (Trucks/Drivers/Clients/Subcontractors/ClientInvoices/SubcontractorBills, via `AttachmentOwnerType`) — there is deliberately no per-category table (e.g. no separate "contracts" table). Every upload requires a `label` (a human-chosen name) alongside the file — the uploader is responsible for naming it something recognizable; `fileName` separately preserves the original uploaded file's name. Files are served only through an authenticated `GET /api/v1/attachments/:id/download`, not a static mount — these are sensitive documents (CIN scans, bank details, contracts, insurance docs).
- `frontend/src` **has not been touched yet** — it still fully contains the gaming-domain UI (dashboard pages, Zustand stores, service calls for doms/experiences/games/machines/coupons/comments/etc.) targeting backend endpoints that no longer exist. The backend ERP API is now complete, so per the user's explicit ordering this is next: expect most of `frontend/src` (stores, dashboard pages, services outside `auth`/`user`) to be replaced or removed as the ERP frontend is built out against the new `/api/v1/{trucks,drivers,clients,subcontractors,missions,client-invoices,subcontractor-bills,dashboard,permissions,attachments}` endpoints.
- `backend/dist` is stale compiled output from before the module deletions; don't treat it as a source of truth.

**Migration tooling quirk**: `npx prisma migrate dev` does not work in this sandboxed/non-interactive environment — it fails with "Prisma Migrate has detected that the environment is non-interactive" as soon as there's anything to confirm (even a plain additive change, apparently due to unrelated pre-existing drift history). The workaround used throughout this pivot: hand-write the migration SQL (or generate it via `npx prisma migrate diff --from-schema-datasource prisma/schema.prisma --to-schema-datamodel prisma/schema.prisma --script`, which doesn't need a TTY), save it under `prisma/migrations/<timestamp>_<name>/migration.sql`, then run `npx prisma migrate deploy` (also non-interactive-safe) followed by `npx prisma generate`. Always verify with a second `migrate diff` call afterward — it should print "This is an empty migration." when the DB and schema are back in sync.

## Repo layout

Two independent Node projects, no shared root package (root `package-lock.json` is a stub):
- `backend/` — NestJS 11 API (TypeScript, Prisma, PostgreSQL)
- `frontend/` — Next.js 15 (App Router, React 19, TypeScript, Tailwind v4, shadcn/ui "new-york" style)

Run all commands from inside `backend/` or `frontend/` respectively — there is no root-level script runner.

## Backend architecture (NestJS)

Each domain is a self-contained Nest module under `src/<domain>/` with a consistent internal shape:
```
<domain>/
  <domain>.module.ts
  controllers/<domain>.controller.ts
  services/<domain>.service.ts
  dtos/                    # create/update/filter/bulk-delete DTOs, class-validator + swagger decorated
  types/<domain>-response.type.ts
```
For the original `roles`/`users` shape (still used as-is by those two modules) look at `src/roles/`. For any **new ERP module**, `src/trucks/` is the closer template — same file shape, but using `PermissionGuard`/`@RequirePermission` instead of `AdminRoleGuard` (see below); `src/trucks/`, `src/drivers/`, `src/clients/`, and `src/subcontractors/` all additionally show the attachment sub-resource pattern (`AttachmentsModule` imported, `FileInterceptor('file', { storage: memoryStorage() })` on upload routes, a required `label` field alongside the file).

Key conventions used across modules:
- **Auth**: global `AuthGuard` (registered as `APP_GUARD` in `AuthModule`) checks a Bearer JWT on every route unless the handler/class carries `@Public()` (`src/decorator/public.decorator.ts` — note `src/auth/decorator/public.decorator.ts` is a duplicate of the same decorator; both exist). Any module whose controller references the `AuthGuard` class directly via `@UseGuards(AuthGuard, ...)` must also import its own `ConfigModule` + `JwtModule.registerAsync(...)` (copy from `src/roles/roles.module.ts`) — otherwise it fails at **runtime boot**, not at `build`/`lint`, with `UnknownDependenciesException`. Always boot-test (`npm run start`, hit `/api/docs`) after adding a module, not just `npm run build`.
- **Two authorization layers**: `AdminRoleGuard` (`src/auth/guards/admin-role.guard.ts`, used by `roles`/`users`) is a binary check on `roles.name === 'admin'`. `PermissionGuard` + `@RequirePermission(module, action)` (`src/auth/guards/permission.guard.ts`, used by every ERP module) is granular per-`(role, module, action)` via the `Permission` table, admin still bypasses it — this is the one to use for new modules. Manage grants via `PermissionsController` (`/api/v1/permissions/roles/:roleId`).
- **Route layout**: `roles`/`users` split public/read (`@Public()`) from `admin/*`-prefixed writes. ERP modules deviate deliberately: **nothing is `@Public()`** (this is internal ops/financial data), but reads still use `@RequirePermission(module, 'read')` rather than requiring admin — so a non-admin role can be granted read access without full admin rights. Writes stay under an `admin/*` path prefix by convention (`admin/create`, `admin/:id`, `admin/bulk`, `admin/:id/restore`, `admin/bulk-restore`) even though the actual gate is `PermissionGuard`, not `AdminRoleGuard`.
- **API versioning**: URI versioning is enabled globally (`app.enableVersioning({ type: VersioningType.URI })`); controllers declare `@Controller({ path: '<domain>', version: '1' })`, giving routes like `/api/v1/roles/...`.
- **Soft deletes**: models use a `deletedAt` timestamp rather than hard deletes; filter DTOs commonly expose a `showArchived` boolean to toggle between active/archived records, plus `offset`/`limit`/`search` pagination and a free-text `status` filter (see `src/users/dtos/filter/filter-params.dto.ts`). Services expose `restore`/`bulkRestore` alongside `remove`/`bulkDelete`. Exception: `Attachment` rows are hard-deleted (the underlying file is deleted from disk at the same time, so a "soft-deleted but file gone" state would be meaningless).
- **Passwords**: hashed/compared via `src/helpers/helper.helpers.ts` (`hashPassword`/`comparePassword`, bcrypt-based).
- **Prisma access**: no repository layer — services inject `PrismaService` (`src/prisma/prisma.service.ts`) directly and call `this.prisma.<model>....`.
- **Validation**: global `ValidationPipe` with `whitelist`, `forbidNonWhitelisted`, and `transform` enabled — DTOs must declare every accepted field with `class-validator`/`class-transformer` decorators or requests get rejected.
- **Env vars**: `JWT_ACCESS_SECRET`, `JWT_EXPIRATION_TIME`, `DATABASE_URL`, `UPLOADS_DIR` are read via `ConfigModule`/`ConfigService` (global). `backend/.env.example` documents these.

## Frontend architecture (Next.js)

- App Router under `src/app`; the authenticated area lives under `src/app/dashboard/*`, one directory per domain, gated client-side by `src/app/dashboard/layout.tsx` (redirects to `/` if `useAuth()` reports unauthenticated).
- `src/hooks/use-auth.ts` is a localStorage-backed auth hook (`access_token`/`user_email`/`user_name` keys) — there's no cookie/session-based auth or context provider; any component needing auth state calls this hook directly.
- `src/lib/utils.ts` exports a shared `axiosInstance` (Axios) that attaches the bearer token from `localStorage` on every request and, on a 401 response, clears auth keys, toasts via `sonner`, and hard-redirects to `/`. Use this instance (not a bare `axios` import) for any new API call so 401 handling stays consistent.
- `src/services/*.service.ts` wrap `axiosInstance` calls per domain (currently only `auth.service.ts` and `user.service.ts` are current; the rest of the domain UI reads/writes through `src/stores/*` directly — see the pivot note above).
- `src/stores/*` are Zustand stores, one per domain, used as the primary client-side data layer for dashboard pages (most of these target the now-deleted gaming-domain backend endpoints — see status note above).
- `src/components/ui/` is shadcn/ui (`components.json`: style `new-york`, base color `neutral`, icon library `lucide`); other `src/components/<domain>/` folders hold feature-specific tables/forms per domain, generally named `enhanced-<domain>-table.tsx`.
- `NEXT_PUBLIC_API_URL` controls the API base URL the frontend targets (set at build/run time; see `docker-compose.yml` for the containerized value `http://localhost:8459/api/v1`).
